# Privacy and permissions

The reusable engineering baseline this project follows has no rule for
browser-extension permissions or privacy, so the controls below are
project-local. They are requirements on every change, not a description of one
release.

## Permissions requested

| Manifest entry | Why it is needed | What it does not allow |
| --- | --- | --- |
| `content_scripts` matching `https://chatgpt.com/*` and `https://claude.ai/*` | Read the conversation text on the page to decide direction, and add presentation attributes. Both browsers show this as access to data on these two sites. | Any other site, and any subdomain of these two. There is no all-sites pattern, no wildcard host and no `host_permissions` entry. |
| `storage` | Remember the reader's preferences in the browser's local extension storage. | Synchronisation to an account (`storage.sync` is not used). |

Nothing else is requested: no `tabs`, `activeTab`, `scripting`, `webRequest`,
clipboard, microphone, notifications or native messaging, and there is no
background script.

The match patterns are exactly the hosts of the site adapters in
`src/page/sites/`; a test fails if the manifest and the adapters disagree or if
anything broader is requested.

Firefox builds declare `data_collection_permissions: { "required": ["none"] }`.

## Data handling

- **Processed in memory, never stored or sent:** the text of the conversation,
  read only to count words by script. On Claude only message content is read;
  on ChatGPT, paragraph-like text in the main region.
- **Stored:** one object under the key `readela.preferences` — on/off,
  direction mode, font, size, spacing and a format version. Unknown fields are
  dropped before saving. No message content, page address, site name or
  history is stored. The same object serves both sites.
- **Sent anywhere:** nothing. The extension has no backend and makes no
  network request.

## Controls

1. No network API in shipped code (`fetch`, `XMLHttpRequest`, `WebSocket`,
   `sendBeacon`, `EventSource`), and no address other than the match patterns
   and the homepage address in the manifest metadata.
2. No remote or dynamic code: no `eval`, `new Function`, remote script or
   remote stylesheet. All code and styles are packaged files.
3. No unsafe HTML insertion: no `innerHTML`, `outerHTML`,
   `insertAdjacentHTML` or `document.write`. The page is changed only through
   `data-readela-*` attributes and, on a mirrored list or quotation,
   `--readela-*` custom properties.
4. Text nodes and page-owned attributes are never written.
5. Editable fields — the composer, text areas, inputs and anything
   `contenteditable` — are never read or marked, on any site.
6. No font or other third-party asset is bundled or downloaded. Font choices
   name fonts already installed on the device. The icons are generated by
   `scripts/make-icons.mjs` from original geometry.
7. Development dependencies (the bundler and the browser-automation library)
   are not part of the packaged extension.
8. Adding a permission, a match pattern, a stored field or a network request
   requires updating this document and the Product Brief in the same change.

## How these are verified

- **Source review:** a search of `src/` for the APIs in controls 1–3; the
  result is recorded in the dated evidence under `docs/evidence/`.
- **Contract test:** `test/page/sites.test.mjs` checks the manifest against the
  site adapters and the exclusion of editable fields on every site.
- **Runtime check:** the end-to-end suite serves a synthetic conversation page
  for each site with no external resources, refuses and records every other
  request, and asserts that none occurred; it also asserts that storage holds
  only the preferences object. On the real sites, requests are attributed by
  initiator so the page's own traffic is not mistaken for the extension's.

Public source makes these claims inspectable. It is not by itself a security
guarantee.
