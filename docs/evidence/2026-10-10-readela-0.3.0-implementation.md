Work unit: ENT-240, under the Preflight Record
`docs/project-preflight/ent-240-readela-0.3.0-reading-comfort.json`.

0.3.0. It is dated evidence, not a statement of current status. Nothing in it
is a claim of publication: 0.3.0 was not submitted to any store, tagged or

## Three kinds of statement in this file

## Owner decisions applied

DEC-136 and DEC-116, and the owner's instruction of 2026-10-10 recorded in
ENT-240: independent reading aspects with one unchanged state called Original
and no per-aspect switches; direction Original / Auto / RTL / LTR; reading

## Observed on the real sites

Read-only, in the owner's signed-in Chrome on 2026-10-10: element names,
attribute names and computed colours of one conversation page on each site. No
conversation text was recorded.

- **ChatGPT.** Each reply's text is in a container marked
  `data-markdown-text-style="assistant-message"`, whose direct children are the
  paragraphs, lists and wrappers of the reply. A heading kept for screen
  readers (`h4.sr-only`) sits outside that container, in the frame of every
  turn. Message controls are outside the container. A code block is a wrapper
  with its own background and no `pre` element. A table sits in three nested
  wrappers. The reader's own message is not made of paragraphs. The site's
  dark theme has a pure black page background. The attribute
  `data-message-author-role`, which the adapter's own-message selector names,
  was not present.
- **Claude.** Messages carry `data-testid="assistant-message"`; the text is in
  a `.standard-markdown` container inside it; paragraphs carry a `dir`
  attribute of the site's own. The site's dark theme has `data-mode="dark"` on
  the root element.

What followed from it: the reading surface is the container that directly
holds a reply's reading blocks, found structurally; a block the site takes out
of the flow never makes a surface (otherwise the frame of a turn would be
coloured); a part of a reply that is not a reading block is given the site's
own measured background and text colour (which is what makes the `pre`-less
code block readable under a theme). The first reply of the ChatGPT test
conversation was given the same frame, so the automated checks exercise it.

The theme rules alone were also applied by hand to those two pages, with the
site in its dark theme, and looked at: Paper and Night coloured the replies
only; the sidebar, the composer, the message controls and the reader's own
messages kept the site's colours; a table and inline code were readable. This
was a look at the stylesheet on real structure, not a run of the 0.3.0
extension there: the installed extension in that browser was 0.2.1.

## Verification

- `node .governance/dev-standards/verify-dev-standards.mjs`: passed.
- `npm test`: 48 tests passed (core rules, preference migration, palette
  contrast, reading-mark logic, stylesheet and manifest contract).
- `npm run test:e2e -- --live`: **42 checks passed in Chrome and 42 in
  Firefox**. The Firefox suite was additionally run five times in a row and
  the Chrome suite twice, all passing. In Chrome the popup is operated with
  real pointer and key input; in Firefox the installed popup is operated
  through its DOM, and keyboard and contrast are checked on a stand-in
  rendering of the same files, as before. What the checks cover that is new in
  0.3.0:
  - **Migration and defaults:** in the unit tests, every version 1 preference
    object keeps its direction, size and spacing; `sans` stays `sans`; `serif`
    becomes the page's own font; the theme starts unchanged.
  - **Direction:** Original leaves the page's own direction and first-strong
    handling while size still applies; Auto, RTL and LTR as in 0.2.1.
  - **Readela Sans:** Persian and Arabic text measures differently in the
    packaged face than in a fallback, and Latin and Hebrew text does not, in
    both browsers; code keeps its font.
  - **Paper and Night**, on both synthetic conversations, with the page light
    and dark: surface, text, link, inline code, table header and selection
    colours; primary text at 10:1 or better; links underlined; the `pre` code
    block and the `pre`-less code block on the site's own background with the
    site's own text colour; navigation, page controls, the composer, the
    reader's own message and the frame of the turn unchanged; a table's
    wrapper part of the same surface; Original restores every colour and
    leaves nothing on the root element.
  - **Reading mark:** saved from a selection and from the first paragraph in
    view; stored as fingerprints with no text or address; one mark per
    conversation; the bar on the leading edge in left-to-right and
    right-to-left paragraphs; Go to mark brings the place into view with a
    temporary emphasis, and with reduced motion immediately and without
    animation (Chrome); found again after a reload, a re-render, and leaving
    the conversation and returning; approximate when only the marked paragraph
    changed, with a broken bar and the popup saying so; not found when a
    neighbour changed too, with no scrolling and the saved place kept; clear on
    Paper and Night with text still at 10:1 on its tint; hidden while Readela
    is off and back when it is on; the only mark on the page when every aspect
    is Original; Clear removes it, after which new content is not read.
  - **Off and privacy:** off leaves no attribute and no custom property; the
    first reply's markup is byte-for-byte the page's own; the pages made no
    request other than the fixture documents and the packaged font; storage
    holds only `readela.preferences` and `readela.marks`.
  - **Popup:** every control reachable and operable from the keyboard in tab
    order with a 3px focus ring; text contrast at least 7.26 in light and 8.2
    in dark; no horizontal overflow at 320px; content height at most 600px.
- **Source review** of `src/` for `fetch`, `XMLHttpRequest`, `WebSocket`,
  `sendBeacon`, `EventSource`, `eval`, `new Function`, `innerHTML`,
  `outerHTML`, `insertAdjacentHTML`, `document.write`, `createElement` and
  `append`: no use; the one match is the word "fetched" in a comment.
- **Live start pages, signed out, nothing typed or sent** (`--live`): the
  content script ran on `chatgpt.com` and `claude.ai` in both browsers; no
  editable field was touched; no request was initiated by the extension. In
  headless Chrome both sites showed a bot check; in Firefox the ChatGPT start
  page and the Claude sign-in page loaded.

## Not verified

- The 0.3.0 extension itself on a real signed-in conversation. The owner's
  visual review of the local build covers this.
- The minimum browser versions declared in the manifests (Chrome 121, Firefox
  140).
- A mark surviving a browser restart was not automated; it rests on the
  browser's local extension storage, which the reload check reads back.
- Reduced motion in Firefox, which the automation protocol cannot switch.

## Findings and their disposition

- **Fixed in this work.** A screen-reader heading in the frame of a turn made
  the whole frame a reading surface (found on the real ChatGPT structure).
  The popup could show a first status report after the result of a quicker
  action; requests are now answered in order, and the popup says "Marked" only
  after the mark is stored.
- **Accepted limits, recorded in the README.** Under a theme opposite to the
  site's own, a code block stands out as a block of the site's colour. Colours
  the site gave to individual words in a reply are replaced by the theme's
  text colour. The reader's own messages are not themed. A mark in a
  conversation whose earlier messages are not on the page yet is reported as
  not found until they are. The mark is not announced in the page to a screen
  reader.
- **Carried, outside this scope.** On the ChatGPT page observed, the adapter's
  own-message selector no longer matches, so the reader's own messages there
  are not given a direction. This predates 0.3.0 and the README already says
  that only known layouts are handled. Revisit trigger: the next adapter
  change, or an owner report that own messages read in the wrong direction.
- **Carried to release preparation.** The listing images show the 0.2 popup
  and are regenerated before a 0.3.0 submission.

No wide-audit trigger fired: the change is confined to the declared scope, and
its trust-relevant parts are covered by the targeted checks named in the
Preflight Record.
