## Observed on the real sites

Read-only, in the owner's signed-in Chrome on 2026-10-11, a fourth time:
element names, attribute names, computed styles, geometry and counts. No
conversation text, title or address was recorded. Nothing was typed or sent.
The build of `d9d4542` was installed in that browser. The tab used was not in
view.

**Claude: why no row was marked**

- The sidebar's list held 28 conversation rows, each a link
  `a[data-row-main-button]` under an element with `data-row-key`. For 24 of
  them the link's address was `/cowork/cse_<id>`; for 4, `/chat/<uuid>`.
- Clicking a row of the first kind showed the conversation at
  `/chat/<uuid>`. That row was then the only link with
  `aria-current="page"`, and its address was still `/cowork/cse_<id>`.
- No attribute of the row or of its ancestors held the uuid, and the two
  identifiers were not the same number in another notation (the `cse_`
  identifier read as base 58 gives 32 hexadecimal digits that differ from the
  uuid in 27 of 32 places).
- The installed build's marking was running: an attribute set by hand on a
  row of a conversation without a bookmark was removed again within a second.
  A hand-set mark was drawn as designed (6 by 11 pixels, at the row's left
  edge). So the rows of bookmarked conversations were not marked because no
  key could be derived from their address, and for no other reason.
- The site's own navigation (New, Projects, Artifacts and others) uses the
  same link hook, without a `data-row-key` ancestor.
- Geometry: the list clips 4px from the sidebar's edge; a row link begins at
  8px and fills its row; its text begins at 14px. On ChatGPT a row link
  begins 10px inside its row.

**ChatGPT: why inline code vanished under a theme**

- In a conversation with 31 pieces of inline code there was no inline `code`
  element. Each was `span[data-markdown-copy="inline-code"]`, with a `dir`
  attribute, a translucent background and corners of 6px.
- The theme rules of `d9d4542` named `code`, `kbd` and `samp`. A span was
  ordinary reading text to them: it was given the text colour and its
  background was removed. Under Readela Sans it was also given the reading
  font.

**Both sites: a change of conversation is reported by the browser**

- With a listener for the Navigation API's `currententrychange` added in the
  page, choosing another conversation in the sidebar raised the event on both
  sites: twice for each change on ChatGPT; on Claude once for the row's own
  address (`/cowork/cse_<id>`) and once for the address the conversation is
  then shown at (`/chat/<uuid>`), with the same single row marked
  `aria-current` both times.
- Browser support, from MDN's compatibility data read the same day: Chrome
  102, Firefox 147. The manifests' minimum versions are Chrome 121 and
  Firefox 140, so Firefox 140 to 146 take the other path. A probe confirmed
  the API is present in Firefox 157 and absent with
  `dom.navigation.webidl.enabled` set to false, which is how that path is
  run in the tests.

## What was corrected

### Bookmark: the name, the popup

The feature is called Bookmark wherever the reader sees it. Internal names
(`mark`, `place`) are unchanged.

- Heading `Bookmark`, with the total beside it and nothing else: `7 total`.
  The total is of all stored places, both sites together, read by the popup
  from storage and following it.
- Buttons: `Bookmark`, `Return`, `Remove` where this conversation has no
  bookmark, the last two unavailable; `Update`, `Return`, `Remove` where it
  has one. Accessible names `Return to bookmark` and `Remove bookmark`. No
  words say whether this conversation is bookmarked.
- One helper line: "Marks your reading position in this conversation." The
  rule for which paragraph is taken is in the first button's tooltip.
- Results: "Bookmarked." the first time and "Bookmark updated." after that;
  "Returned to your bookmark."; "Bookmark removed."; at the limit "All 1000
  bookmarks are in use. Remove one to bookmark this conversation."
- One line for the shortcut: `Shortcut: Not set` with `Set shortcut`, or the
  key the browser holds with `Change`.

### Line spacing

Original, 1.5, 1.75, 2.0 (from Original, 1.6, 1.9, 2.2). A stored 1.6, 1.9
or 2.2 is read as 1.5, 1.75 or 2.0 by one small table in
`normalizePreferences`; the stored object's format and version (2) are
unchanged, and nothing is rewritten in storage until the reader next changes
a setting. Where it applies is unchanged: reading blocks, including table
cells; not code blocks.

### Claude sidebar bookmark

- **Cause:** as observed above. The earlier build recognised a row only by
  deriving the conversation's key from the row's address, which most of
  Claude's rows do not allow.
- **Correction.** The Claude adapter now says how the site marks the row of
  the conversation shown (`rowShown`: `[aria-current="page"]`) and limits
  rows to links under a row key, which leaves the site's navigation out. A
  row whose address names its conversation is recognised as before. For any
  other, a one-way fingerprint of the row's address path is kept with the
  place, as an optional eleventh value (`r`), and a row whose fingerprint a
  stored place names is marked.
- **When the fingerprint is written.** When the reader bookmarks or updates,
  if the site marks exactly one row as shown and that row's address does not
  name a conversation. And once by itself: when the stored place of the
  conversation shown names no row or another, and the same single row has
  been seen marked as shown twice, half a second or more apart. Only that
  value changes. This is the one write to storage that no button asked for;
  it is what makes a bookmark saved by an earlier build, or saved while the
  list was not showing, appear once its conversation is opened again.
- **Stored format.** Version 2, unchanged. A place without the value is
  stored exactly as before, byte for byte; a value that is not a fingerprint
  is left out. No title, label or address is stored.

### The bookmark's size and place

About 8 by 14 CSS pixels (`0.5rem` by `0.875rem`), from 6 by 11, the same
shape and colour on both sites, still a pseudo-element with no pointer input
and no part in the row's layout. On ChatGPT it is at the row's start, where
the row has 10px before the link. On Claude the adapter asks for the edge
placement, 4px further out: from 4px to 12px, inside what the list shows and
2px clear of the text.

### The key, and the command

- **Removed:** the listener for Alt+Shift+S, its constant, its text in the
  popup and its checks. The page code names no key; a test fails if it does.
- **Added:** one command in the manifest, `bookmark`, with a description and
  no suggested key. In Chrome it is unbound until the reader assigns a key at
  `chrome://extensions/shortcuts`; in Firefox, in Manage Extension Shortcuts.
  The browser stores the key and refuses what it does not allow (Firefox
  refused a single letter in a probe, with its own message).
- **The popup** reads the key with `commands.getAll` and opens the browser's
  settings: `commands.openShortcutSettings` in Firefox (from version 137; the
  manifest's minimum is 140); in Chrome, which has no such call, the page
  `chrome://extensions/shortcuts` in a new tab, which needs no permission.
  If neither works it says where to look. There is no field that takes a key.
- **The background component** is one file of 1,163 bytes built from
  `src/background/main.js`: a service worker in Chrome, a script that is not
  kept running in Firefox. It registers one listener, for the command, and
  sends one message, `quick`, to the tab the browser names. The page runs
  the same function as the popup's button and shows the brief emphasis once
  the place is stored. It keeps no state, sets no timer, makes no request
  and stores nothing. In a 60-second trace of an idle page, no call into
  `background.js` occurred in any state measured (the column "background
  calls" below is 0 throughout).

### Return: the end of the scrolling region

Found while the fixtures were changed, and not reported by the owner. The
search decided it had reached an end of the region when the position was
within half a pixel of it. A browser reports the region's size in whole
pixels and the position in parts of a pixel, so on a layout with fractional
heights the two do not meet: the search then never saw the beginning, did
not wait there for the site to load more, and repeated the same move until
its 30-second limit. It is now at an end within two pixels, or when a move
no longer moves. On the fixture that showed it, a search for a place that is
not there ends in 3.3 seconds instead of 30.

## Performance and resource use

### What was asked, and what could be measured

Readela is meant to stay switched on, so what it runs while nothing happens
matters most, then what it adds while the page works, then whether anything
grows.

- **Measured in Chrome**, in detail, on synthetic pages.
- **Measured in Firefox**, coarsely, by the processor time and memory of the
  browser's processes.
- **Unavailable:** the same on real signed-in conversations. This build
  cannot be installed in the owner's browser by this work, the automated
  browsers are not signed in, and the tab available for observation there is
  not rendered. The synthetic pages are built after what was counted on the
  sites (about 440 nodes for a turn; 23 to 28 conversation rows), and the
  sites' own scripts, which dominate a real page's work, are absent. What is
  reported is therefore what Readela adds, not what a real page costs.

### Method

`test/perf/run.mjs` (npm script `perf`) starts the installed Chrome headless
with a fresh profile, loads the unpacked extension, and serves
`test/perf/fixtures/page.html` for `chatgpt.com` and `claude.ai`; every other
request is refused. The page builds a conversation in the structure each
adapter expects: 12 turns of about forty blocks each (headings, mixed Persian
and English paragraphs with inline code, emphasis and links, lists, a code
block, a table, a quotation), 28 rows in the sidebar; "long" is 60 turns
(about 19,000 nodes) and 300 rows. It can stream a reply word by word,
replace sidebar rows, change conversation without a page load, type into the
composer and scroll.

- **Scripting by origin.** A trace of the page's renderer process
  (`devtools.timeline`) records every entry into a script with the script's
  address. Entries into the extension's files are Readela's; their count and
  summed time are reported as "Readela calls" and "Readela ms". This
  attribution is exact for calls and good to a fraction of a millisecond for
  time. Layout and style work caused by Readela's marks is not attributed by
  the trace; it shows as the difference from the baseline's layout and style
  time.
- **Processor time** of the page's process, from the browser
  (`SystemInfo.getProcessInfo`), as a share of the window. At idle these
  values are a few hundredths of a percent and their run-to-run variation is
  as large as the differences between states; they are reported with their
  range and not relied on alone.
- **Memory.** The JavaScript heap of the page's process after a forced
  collection (`Performance.getMetrics`), which includes the content script;
  DOM nodes and listeners; and the process's private memory from the
  operating system. Private memory of a browser process moves by megabytes
  from run to run for reasons unrelated to the page; small differences are
  not meaningful.
- **Windows and repetition.** Idle: after 6 seconds of warm-up, three
  windows of 60 seconds; the median is reported, with the range for
  processor time. Workloads: three passes each, median. The long run: 15
  minutes.
- **Baseline.** A browser without the extension, the same page, the same
  script.
- Tracing adds a little work of its own, the same in every state.

### Before and after

"Before" is the build of `d9d4542`, measured the same day by the same script
(`--extension` pointing at its unpacked folder). Five things were found by
reading the code against these measurements, and changed:

1. **Every lookup of this conversation's place validated every stored
   place.** `findMark` normalised the whole stored object on each call, and
   it was called on every beat and after every batch of changes: with 1000
   bookmarks, about 250 microseconds a call. The reader now holds an index
   by conversation, built when the stored places change; a lookup takes
   about 0.01 microseconds whatever the number.
2. **The lists were scanned every second**, and a set of all stored keys
   was built each time. They are now looked at when a row link is added or
   its address changes, when the stored places change, and when Readela is
   switched.
3. **A timer ran every second and did everything each time**: found the
   conversation region again, looked the place up, scanned the lists. Where
   the browser reports a change of address itself (the Navigation API:
   Chrome, and Firefox from version 147) there is now no timer at all on a
   settled page; the event starts a few beats, a second apart, which look at
   the page and stop. Where the browser has no such event (Firefox 140 to
   146) the beat remains, compares the address path with the one last seen
   and returns. Neither runs while the page is out of view.
4. **Typing was handled like streaming.** Each keystroke in the composer was
   a change to the document that was queued and handled. Changes in an
   editable field are now dropped as they arrive.
5. **Each kept unit made the browser lay the page out.** A code block or
   other unit that stays the site's was marked, measured and marked again,
   one after another, and each measurement between two writes forced a
   layout. They are now marked together, measured together and marked
   together, as are the lists and quotations whose indentation is checked.
   The conversation region is also found once for a pass and not once for
   each part of it. In a profile of eight re-renders of a 12-turn
   conversation under Night with Readela Sans, measuring the units took 259
   of 433 ms before and 166 of 388 ms after; what remains is the one layout
   and one style pass the browser owes the new content in any case, which
   Readela's first reading brings forward.

What the long runs show, and what they do not:

- **Nothing that Readela itself holds grew.** Its JavaScript heap stayed at
  2.1 MB for the hour, the number of DOM nodes and of listeners did not
  change, and what is held in malloc rose by 1.6 to 2 MB in the hour.
- **The process's memory did rise, steadily, for the whole hour**: from 70 MB
  to 143 MB on the ChatGPT page and to 170 MB on the Claude page, against a
  rise of about 6 MB without the extension. This is a real increase (the
  working set rose with it), it had not levelled off when the run ended, and
  it is the one result of this audit that does not meet the aim of a bounded
  cost.
- **Where it is.** Not in anything held: what the browser's collected heap
  holds rose by 2.3 MB (1.1 MB without the extension), and nearly all of that
  is media-query objects. The rise is in the pages that heap has taken and
  keeps: 30 MB to 99 and 126 MB.
- **Media-query objects** are retained by the browser itself each time the
  document is restyled. The page alone accumulates them (0.05 → 1.18 MB in
  the hour without the extension); a page script that flips an attribute on
  the root element 340 times, with no extension, accumulated 0.69 MB of them
  and 8 MB of heap pages. Readela's marks make the browser restyle a
  conversation once more after the site has rendered it, and the rate
  doubles. Removing Readela's own `@media` rules or its `@font-face` rules
  from the stylesheet did not change it; removing the stylesheet did.
- **What drives the pages.** Runs of single parts of the cycle, repeated as
  fast as they complete, under Night with Readela Sans except for the first
  row, each sampled the same way:

  | Part of the cycle, repeated | Repetitions | Pages of the collected heap | For each repetition |
  | --- | --- | --- | --- |
  | A conversation rendered anew, no extension | 294 | 15 → 26 MB | about 38 KB |
  | A conversation rendered anew | 859 | 21 → 49 MB | about 33 KB |
  | The same, then bookmark, update and remove | 775 | 21 → 86 MB | about 84 KB |
  | The same, then bookmark and return | 276 | 24 → 65 MB | about 147 KB |
  | Bookmark, update, return and remove on a page that does not change | 295 | 19 → 21 MB | under 10 KB |

  Rendered as fast as it will go, a conversation costs the heap about the
  same with and without the extension. The bookmark actions are what the
  extension adds: roughly 25 KB of kept pages for a bookmark and 90 KB for a
  return, when they follow a newly rendered conversation. Each of them reads
  the box of every element on the page at least once, to find what covers
  the reading area, and the boxes are objects in that heap. At the pace of
  the cycle and without bookmark actions, three 30-minute runs rose by
  10 MB and then stayed level (Night with Readela Sans), by 16 MB and still
  slowly rising (defaults), and by 20 MB and then level (no extension): the
  browser's heap behaves differently from run to run, with and without
  Readela.
- **In proportion.** The hour is 567 conversations rendered anew, about 1,130
  bookmarks and updates, 280 returns and 567 removals: one every second and
  a half, without pause. A reader who changes conversation a hundred times a
  day and bookmarks or returns twenty times adds, at these rates, a few
  megabytes a day at most to a page that stays open; a tab that is reloaded
  starts again.
- **Variation.** A second one-hour run of the same cycle under Night with
  Readela Sans rose from 72 MB to 98 MB and stayed there from the thirtieth
  minute; one under the defaults rose from 65 MB to 135 MB. The 15-minute
  runs rose by 11 to 13 MB without setting changes and by 26 to 37 MB with
  272 of them, each change of a setting being a restyle of the whole
  conversation.
- **Not established:** whether the browser gives these pages back over a
  longer time, on a page that is left alone, or when the system is really
  short of memory; the simulated notice of pressure did not return them
  within seconds. Whether the same happens on the real sites, whose own
  scripts restyle far more than this page does.
- **By the owner's rule** a rise without end over a long run is a blocker.
  This rise is tied to what is done to the page, not to time: an idle page
  does not grow (idle, above). It is recorded here as an open finding for
  the owner's judgement, with two ways to reduce it that were not taken in
  this pass: read fewer boxes for a bookmark and a return (the search for
  what covers the reading area looks at every element); and mark blocks
  before the browser first lays them out, which would also remove the
  second layout.

  is the typography the owner approved. No change was made.

## Privacy and trust effect

  list. No title, text, address or site identifier is stored. Fingerprints
