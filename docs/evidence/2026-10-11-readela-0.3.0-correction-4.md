## What was corrected

### Who owns what under a reading theme

The rule is the one the product already had for a code block, applied to
everything: Readela colours the reading text it recognises, and every other
part of a response stays the site's, whole.

- **Units.** The ChatGPT adapter names the component kinds that are text
  (`text`, `title`, `caption`, `code`, `list`, `list-item`, `table`,
  `table-row`, `table-cell`, `blockquote`, `icon`), anything carrying
  `data-d-text-flow`, and anything set inline in a sentence. Every other
  component, of a kind seen or not, is a unit: nothing inside it is read as
  text, given a direction, a font or a size, or coloured. Only the outermost
  unit carries the mark.
- **Wrappers.** A wrapper is part of the reading surface only if it holds
  reading blocks and no text of its own; one that carries text outside
  reading blocks is a unit. This is the general safeguard for a layout no
  adapter knows.
- **The site's ground behind a unit.** A unit that does not bring an opaque
  background gets the site's own measured background behind it where it
  shows text (the label of a control now counts), where it holds a drawing at
  least 48px each way (an `svg`, a `canvas`, or an `img`, which is how the
  site's diagrams arrive), and where it has a see-through tint of its own (a
  divider). A row of controls that shows nothing but icons gets none, as
  before. Its corners and its text colour are kept as before.
- **Forms.** A reply is no longer left uncoloured because a form is somewhere
  in it: a form shut inside a unit is that unit's business. A form that is
  not inside a unit still rules the surface out. Nothing in a form is read
  or written.
- **A caption** that the site sets as a `span` directly in a column is read
  as a reading block.
- **Tokens.** Table lines were 1.91:1 (Paper) and 2.25:1 (Night) against the
  surface. They are now `#8C816B` (3.35:1 against the surface, 3.06:1
  against a header cell) and `#7E7568` (3.53:1 and 3.14:1). The bar of a
  quotation is coloured also where it is the border of a generated box
  (4.27:1 on Paper, 4.98:1 on Night, unchanged colours).
- **Not done, on purpose:** no component of the site's is recoloured, and
  there is no rule for any one widget. A card on Paper is a card in the
  site's colours on the site's ground, like a code block.

What this looks like: on a dark site under Paper, the paragraphs, headings,
lists, tables, quotations and captions of a reply are dark text on Paper,
and each card, chart, poll and divider is a block in the site's own dark
colours.

### Auto direction

- Nothing inside a unit takes a direction from Readela, in any mode, so the
  site's own layout decides there. This is what puts 2M and 103K back.
- A figure with its unit attached (one or two letters directly after
  digits: 2M, 103K, 4.5GB, 10x) is a number, not a word. Alone in a block it
  follows what is around it, like any other number; in a sentence the words
  still decide. A word that merely holds digits (COVID19, v2, 100Mbps) is
  still a word.
- Auto is still the default, and paragraph-level direction elsewhere is
  unchanged: in the component form an English paragraph in a right-to-left
  reply reads left-to-right.

### Bookmark

- **Popup.** The first action reads `Save` (accessible name `Save
  bookmark`), then `Update`; `Return` and `Remove` and the total are
  unchanged. The first result reads "Bookmark saved.".
- **Commands.** Three, each without a suggested key: `bookmark` (save or
  update; the name is unchanged, so a key assigned to it stays with it in an
  installed copy), `bookmark-return` and `bookmark-remove`. The background
  component passes each to the page function the popup's button calls; it
  still registers one listener and nothing else. After a return the
  paragraph returned to shows the same brief emphasis as after the popup's
  Return. The popup lists the keys the browser holds
  (`Shortcuts: Save Ctrl+S, Return Alt+R`, or `Not set`) and opens the
  browser's own settings.
- **A control in the page: evaluated, not built.** DEC-143 asked for one
  small control in the site's own interface for the three actions, if it
  could be done without fragility, and for the tradeoff to be reported
  otherwise. What was found:
  - Readela's footprint in a page is attributes and custom properties; it
    creates no element. A control that can be clicked and focused is an
    element. A generated box on one of the site's elements can be drawn but
    cannot be focused, has no name for a screen reader, and can be clicked
    only by intercepting clicks on the site's element under it.
  - The place for it is the bar over the conversation. On ChatGPT that is a
    header the site's framework renders, one for each conversation it keeps,
    with no hook that names its actions; on Claude it is an unnamed element
    the pointer passes through. An element put there is inside what the
    site redraws; it would have to be put back whenever the site does, and
    whether the site tolerates it could be checked from here on neither
    site, because this build cannot be run on them by this work.
  - A fixed overlay is the floating control DEC-143 rules out. An entry in
    the browser's right-click menu needs one more permission and was left
    out of this correction by ENT-246.
  - So it was not built. The three actions are reachable without the popup
    by command. The decision this needs from the owner is among: an element
    in the sites' own bars, accepted as a change of the product's footprint
    and tried on the real sites before release; a right-click menu, with its
    permission; or commands and popup only.

## Memory

### What was recorded for `73ec2c3`

In a one-hour run of a paced cycle the page's process grew from 71 to 143 MB
(ChatGPT-shaped page) and from 70 to 170 MB (Claude-shaped), against about
6 MB without the extension, with the JavaScript heap, the DOM nodes and the
listeners flat. The growth was in pages of the browser's collected heap
(30 to 99 and 126 MB), not in what that heap held (6 to 8 MB).

### What was found

The measurements are of Chrome 154 on the synthetic page of
`test/perf/run.mjs`. "Pages" is the memory the browser's collected heap has
taken (`blink_gc/main/heap` in a memory dump, after two forced collections);
"held" is what is allocated in it. The loops below repeat a part of the cycle
as fast as it completes for three minutes, which is far harder on the
browser than a reader is.

1. **The geometry read for a bookmark was a small part.** Every Save and
   every Return measured the box of every element of the document to find
   what covers the edges of the scrolling region, and the box of every
   reading block to see whether it is shown. Limiting the first to the
   application around the conversation and replacing the second by a
   question that hands out no box lowered the growth of a loop of bookmark
   actions by about an eighth. It was done (below) and it was not the cause.
2. **The page grows without any extension.** Showing another conversation
   400 times in a browser with no extension took the pages of that heap from
   18 or 19 MB to 51 MB in one run, to 97 MB in another and to 106 MB in a
   third (on the page without its two media rules), with 4 to 5 MB held.
   What is kept depends on how fast the page is rendered anew and differs
   widely from run to run.
3. **The browser keeps a little for every table it styles from scratch.**
   Listing the dump by class showed what the "media-query objects" of the
   earlier evidence are: one `MediaQuerySet` with its queries, about 190
   bytes, for each `table` element whose style is worked out afresh, with no
   extension and no style sheet of Readela's involved (cloning one table in
   place 300 times: 59 KB; nothing for a paragraph, a list, a quotation, a
   code block or a button). Twelve tables in a conversation rendered anew:
   2.2 KB each time.
4. **Readela made the browser style and lay out every new response a second
   time.** It marked a response 60 ms after it arrived, by which time the
   browser had styled and laid it out as the site made it; the marks then
   changed the direction, the font or the colours of everything in it, and
   the browser did both again. So the browser's own retention in 2 and 3
   happened twice for each response: the media-query objects kept were
   exactly double (722 to 737 KB against 374 KB in the same loop), and the
   pages grew two to three times as fast.

### What the earlier evidence had wrong

The earlier file attributed the growth "mostly" to bookmark actions and to
the boxes they read. That was an inference from loops in which only the runs
with the extension selected text and scrolled to it in the page; the runs
without it did not. With the same steps in the page and no extension, part of
that growth is there too, and with the boxes no longer read most of it
remained (item 1). Item 4 is a cause that could be shown and removed; the
one-hour run below shows it is not the whole of it.

### What was changed

- **A response that arrives whole is marked as it arrives**, in the same
  turn of the browser, before the browser has styled or laid it out: a
  conversation shown, an earlier part loaded, a row of a long conversation
  scrolled into the document. The browser then styles and lays it out once,
  with the marks. Marking reads the document and writes marks only; what has
  to be measured (alignment, the mirroring of a list, what a unit needs) is
  read 60 ms later, together, after every mark is written. Text that is
  streamed in is handled as before, in batches.
- **The reading area** for a bookmark is measured from the application
  around the conversation: what a response or a message of the reader's own
  holds is not measured, nor a conversation the site keeps hidden. A Return
  works it out once instead of up to five times.
- **Smaller:** whether a block is shown is asked without a box being handed
  out; the text of a block that holds nothing to leave out is taken from the
  browser in one piece; an element's own style is not asked for where it has
  none.

What the hour shows:

- **Established.** The memory that grows is not held by Readela or by the

- **In proportion.** The hour is 564 conversations shown anew, about 1,130
  saves and updates, 280 returns and 560 removals, one after another
  without a pause longer than half a second. It is a stress, not a day of reading.

## Findings and their disposition

- **For the owner to decide: a control for the bookmark in the page.** Not
  built, for the reasons under "Bookmark". Recorded as OPEN-3 of the
  Preflight Record. Until it is decided, Save, Return and Remove are
  reachable without the popup by the three commands.
- **For the owner to judge: memory.** The gate DEC-143 sets is not
  met by the one-hour run: under Night with Readela Sans the process still
  grew for the whole hour (76 to 152 MB and 69 to 115 MB, against 8 and
  10 MB of growth without the extension), by as much as before on one page
  and by a third less on the other. What grows is free space in pages the
  browser's collected heap keeps, not anything held; the browser does the
  same to the page alone when it is rendered faster; under the defaults no
  growth beyond the page's own was measured. See "Memory". This work does
  not call the build ready for release. What would settle it is one of:
  finding what the packaged fonts add for each render and removing it;
  showing a bound, by a run of several hours and by a page left alone
  afterwards; or the owner's judgement that pages kept by the browser under
  a stress of this kind, with nothing held, are not the growth the gate is
  about.
- **Accepted limits, recorded in the README.** Text inside a card, a poll or
  another part the site lays out itself is not reading text: it takes no
  direction, font or size from Readela, and a bookmark cannot be put in it.
  Under a theme opposite to the site's such a part stands out as a block of
  the site's colour, like a code block. A command given by key shows no
  message when it cannot do what was asked.
- **Left as measured, with the reason.**
  - *The first conversation of a page that is built before the content
    script starts* is still laid out twice. On the sites a conversation
    arrives after the page has loaded. Revisit if a real page shows
    otherwise.
  - *A reply that is re-rendered in place*, inside a root that is already
    there (the end of a streamed reply, on a site that redraws it), is
    marked in the next batch and not as it arrives. Only responses that
    arrive whole are marked at once, so that streaming is not handled word
    by word.
  - *A change of setting* still restyles the whole conversation, with one
    task of 53 to 89 ms at two to four changes in ten on these pages.
  - *Chrome's own retention for each table it styles*: not Readela's to fix;
    it is no longer doubled.
- **Carried to the store-presentation work (ENT-243), not changed here.**
  `docs/store-listing.md` and the manifest `description` still say "reading
  mark"; the listing names one packaged font and does not mention the
  commands or the background component; the listing images show the 0.2
  popup. All of it has to change before any 0.3.0 submission. Revisit
  trigger: the owner's approval of this build.

A full Preflight was performed for this work. Beyond it, no wide-audit
trigger fired: the change is confined to the declared scope; no permission,
match pattern, web-accessible resource, network request or element in a page
was added; what a theme may colour, the two further commands and the moment
at which a response is marked are the trust-relevant parts and are covered
